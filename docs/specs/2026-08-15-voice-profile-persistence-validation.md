# Voice Profile Persistence — Validation Against the Motivating Incident

Task 7 of the `2026-08-15-voice-profile-persistence` plan. Validates that
`voice-profiles/matt-jira.md` (Task 2), applied by hand, actually fixes the
failure that drew the manager's complaint quoted in that file:

> "I would like to see more human in these tickets, and less AI... I lost
> Matt along the way... I don't have the background or time to read the
> amount of content generated by AI... please review the content that is
> put into the tickets, and limit things to relevant information."

Real names and company domains are redacted per Global Constraints; the
underlying incident (a Power Automate flow trigger misconfigured against a
UPN instead of an SMTP address) is preserved because the technical shape is
what the profile's rules are tested against.

## Step 1: Redacted input

This is the redacted stand-in for the original AI-generated ticket synopsis
that drew the complaint — full investigative narrative, technical precision
standing in for rigor, no clear lead with the root cause.

```
Investigation Summary: Email Flow Stall

Over the past several months, the team investigated why the automated
email flow stopped triggering in June. Multiple hypotheses were tested,
including checking the connector authentication method, reviewing the
flow's trigger configuration, examining the account's directory entry,
and comparing the UPN (User Principal Name) against the account's SMTP
routing address. After extensive testing, including building a shadow
connector to isolate the authentication behavior, it was determined
that the flow's trigger was configured against a non-routable UPN
suffix rather than the account's actual SMTP mail domain. Because
Power Automate does not raise an error when a mailbox trigger is
pointed at a non-routable address, the flow appeared healthy in the
UI throughout this period, showing an empty run history that was
indistinguishable from simply having received no mail. This
investigation also involved reviewing directory picker behavior,
which surfaces the UPN by default, likely contributing to the
original misconfiguration. Going forward, all future flow
configurations should be validated against the SMTP address rather
than the UPN to prevent recurrence of this issue.
```

(~179 words, excluding title.)

## Step 2: Rewrite, applying `matt-jira.md` by hand

```
Root cause: The flow's trigger was pointed at the account's UPN
(sign-in address), not its actual SMTP mail address. That UPN wasn't
a routable mail domain, so the flow never actually received anything.

Why it looked fine: Power Automate doesn't error when a trigger points
at a non-routable address. It just shows an empty run history,
indistinguishable from a mailbox that legitimately got no mail. That's
why this sat undetected for months.

Worth noting: the directory picker surfaces the UPN by default, which
likely caused the original mix-up. This isn't a mistake anyone should
feel bad about, it's a trap the tool sets.

Fix: Point the trigger at the SMTP address instead. Going forward,
validate new flow triggers against SMTP, not UPN.

Verification: Send a test message to the SMTP address and confirm the
flow fires.
```

(~137 words.)

Rules applied by hand:
- **Structure** — root cause first, then why it matters, then the fix, then
  verification.
- **Reasoning-chain filter** — cut everything that doesn't help the reader
  decide or act: the multi-month timeline, the list of hypotheses tested
  (auth method, trigger config, directory entry, UPN-vs-SMTP comparison as
  sequential steps), and the shadow connector built to isolate the auth
  behavior. None of that is actionable for the reader; it's how the
  investigator got there, not what the reader needs.
- **Plain language over jargon** — "the flow never actually received
  anything" instead of "indistinguishable from simply having received no
  mail" as an unprompted precision flourish; UPN/SMTP are kept only because
  the fix and verification step literally require knowing which address
  type to use.
- **Trim investigative narrative** — the "multiple hypotheses were tested"
  paragraph is gone entirely, replaced by the single finding.
- **Earned empathetic aside** — kept the directory-picker detail, but
  repurposed it from "here's another thing we checked" (investigative) to
  "here's why this wasn't anyone's fault" (the profile's own worked
  example: "this isn't a mistake anyone should feel bad about, it's a trap
  the tool sets"). This is a deliberate, rule-sanctioned inclusion, not a
  narrative leftover — see the caveat under Step 3, Q3 below.
- **Ending** — closes on the verification step, not a summary restatement.

## Step 3: Check against the manager's stated complaint criteria

**Q1: Is it noticeably shorter than the redacted input?**

PASS. ~137 words vs. ~179 words, about a 23% cut. Not a dramatic
line-count collapse, because the rewrite deliberately keeps two things the
input didn't have: an explicit "why it looked fine" explanation and the
empathetic aside — both required by the profile's own rules, not narrative
filler. The real reduction is in kind, not just count: the entire
"multiple hypotheses were tested" paragraph and the shadow-connector detail
are gone. If judged purely on the removal of investigative bulk, this is a
clear pass; if judged purely on total word count, it's a real but modest
cut. Recording both readings rather than picking the flattering one.

**Q2: Does it lead with the root cause instead of the investigation?**

PASS. First line is "Root cause: The flow's trigger was pointed at the
account's UPN..." — no setup, no "over the past several months," no
"multiple hypotheses were tested" before getting there.

**Q3: Is the multi-step investigative narrative (shadow connector,
directory picker review, hypothesis testing) absent, replaced by just the
finding and a verification step?**

MOSTLY PASS, with a caveat. The shadow connector and the hypothesis-testing
list (auth method check, trigger config review, directory entry
examination, UPN-vs-SMTP comparison as a testing step) are fully cut — the
rewrite states the finding directly instead of narrating how it was found.

The directory picker mention survives, but not as investigative narrative
— it's repositioned as the basis for the earned empathetic aside, which
`matt-jira.md` explicitly calls for when genuinely relevant (its own
worked example is almost this exact sentence). The distinction is real:
the input used "this investigation also involved reviewing directory
picker behavior" (narrating a step taken), and the rewrite uses "the
directory picker surfaces the UPN by default" (stating a fact that
explains why the mistake isn't the engineer's fault). Same underlying
fact, different rhetorical job. Flagging this rather than silently
claiming a clean absence, since a stricter reading of "the investigative
narrative is absent" could reasonably call this a partial fail depending
on how literally "absent" is meant.

**Q4: Is technical precision ("UPN," "SMTP") only used where needed to
act, not piled on for its own sake?**

PASS. Both terms appear only in the root cause (identifying what was
wrong), the fix (what to point the trigger at instead), and the
verification (what address to send the test to). The input's redundant
precision — "User Principal Name" spelled out, "non-routable UPN suffix,"
"SMTP routing address" vs. "SMTP mail domain" as if they were different
things — is gone. The rewrite uses each term once per place it's actually
needed to act.

## Summary

3 of 4 criteria are clean passes. Q1 is a real but modest pass (23%
shorter, with the reduction concentrated in narrative bulk rather than
raw length). Q3 is a pass with a caveat worth tracking: the profile's
"earned empathetic aside" rule and its "trim investigative narrative"
rule pull in slightly different directions when the same underlying fact
(directory picker surfaces UPN by default) serves both an investigative
role and an exculpatory role. `matt-jira.md` resolves this correctly in
its own text — keep the fact, change its framing — and the hand-applied
rewrite followed that resolution. No changes to `matt-jira.md` are
recommended based on this test; the profile did what it was designed to
do. If a future real-world ticket triggers the same Q1/Q3 tension more
sharply, it's worth revisiting as a follow-up, not as a sign this task
failed.
