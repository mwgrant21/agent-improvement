# Voice-Profile Persistence — Design Spec

**Date:** 2026-08-15
**Status:** Draft, pending review
**Author:** Matt + Claude (TokenMonitor session)

## Problem

`humanizer` (the AI-writing-tell removal skill) has a Voice Calibration section that matches a user-provided sample, but it re-analyzes from scratch every invocation — nothing persists. Matt needs his voice matched consistently across contexts (Jira tickets specifically named as the trigger case), across three surfaces (Claude Code, claude.ai GUI, ChatGPT GUI), and across two machines (home, work) — none of which the current design supports.

This gap was identified independently during evaluate-repo passes on `ghostwriter` and `copydesk` (see `humanizer-voice-profile-idea.md` in TokenMonitor project memory) and is backlog item 1 there. This spec covers item 1 only. Items 2-10 (output integrity check, anti-fabrication guardrail, audit-only mode, dual review, learning loop, etc.) are separate, deferred, and unaffected by this design.

### The motivating incident

Matt had Claude's GUI (with a Jira attachment/integration) write a ticket synopsis. His director's response (`jira example.txt`, Downloads):

> "I would like to see more human in these tickets, and less AI... I lost Matt along the way... I don't have the background or time to read the amount of content generated by AI... please review the content that is put into the tickets, and limit things to relevant information."

Matt's own follow-up reply in that same thread is a good structural example of his ticket voice (root-cause-first, a "why this matters" framing, a concrete verification step, an empathetic aside owning that it wasn't anyone's fault) — but not a clean wording sample: Matt confirmed specific phrasing in it ("UPN/sign-in suffix") reads more technical than he'd naturally write, meaning even his own reply had some AI smoothing in it. Structure is trustworthy; exact wording in that one document is not.

## Source material and its reliability

Eight files were read (Downloads + Desktop) to build the profiles. Each has a different reliability for *wording* vs. *structure/instinct*:

| File | Register | Wording ground truth? | Structure/instinct ground truth? |
|---|---|---|---|
| `my voice profile.txt` (Desktop) | General/explaining | Yes — already a deliberate voice guide | Yes |
| `writing samples.txt`, `how I work with AI.txt` (Desktop) | Raw/conversational | Yes — unedited | Yes |
| `voice thoughts.txt` (Desktop) | Live chat/command-mode | Yes — real transcript | Yes |
| `Methodology.txt`, `Philosophy.txt`, `design principles.txt`, `working with ai.txt` (Downloads) | Essay | No — Codex's questions shaped the structure | Yes — substance and values are Matt's |
| `jira example.txt` (Downloads) | Ticket | Partially — some phrasing (e.g. "UPN/sign-in suffix") confirmed not natural to Matt | Yes — root-cause-first, why-it-matters, verification step, empathetic aside are confirmed |

Rule applied throughout: build wording from the "Yes" wording sources; build structure from all of them; never trust a single AI-touched document's exact phrasing as a pattern to imitate.

## Goals

1. A persisted, nameable default voice profile and a Jira/ticket-register profile, stored once, usable everywhere.
2. Works in Claude Code (via humanizer) *and* is portable enough to paste into claude.ai and ChatGPT's GUIs, where no skill or filesystem exists.
3. Syncs to Matt's work machine — where the actual incident happened — not just home.
4. No auto-detection, no YAML, no blending. Matt names the register he wants.

## Non-goals (explicitly deferred)

- Auto-detecting which register applies from context (backlog item 1's stretch goal, from copydesk).
- Structured YAML / tone-dimension scoring.
- Items 2-10 in the humanizer backlog (output integrity, dual review, learning loop, etc.) — separate specs if/when picked up.

## Architecture

### Storage location: `~/agent-improvement/voice-profiles/`

Not `~/.claude/skills/humanizer/` (that folder has no `.git` — nothing there syncs to work) and not TokenMonitor (unrelated repo). `agent-improvement` already has proven pull-rebase/commit/push discipline and already syncs home↔work. New top-level directory, sibling to `domains/`, `loops/`, `skills/`:

```
~/agent-improvement/voice-profiles/
  matt-default.md            # full profile, general/explaining register
  matt-jira.md                # full profile, ticket/professional register
  matt-default-portable.md   # condensed, self-contained, paste into GUI custom instructions
  matt-jira-portable.md      # condensed, self-contained, paste into GUI custom instructions
```

A short pointer file at `~/.claude/skills/humanizer/docs/voice-profiles.md` notes the real location, so the skill's own directory stays discoverable without duplicating content that would drift out of sync.

### Claude Code integration

Extend humanizer's **Voice Calibration** section (`SKILL.md`) with: before asking the user for an inline sample, check whether `~/agent-improvement/voice-profiles/matt-<register>.md` exists for the requested (or default) register, and load it if present. Inline-pasted samples still override, same as today — a fresh sample always outranks a stored profile, matching the existing "a sample outranks this skill's style rules" precedent.

### GUI portability (claude.ai, ChatGPT)

Neither GUI can read `~/agent-improvement/`. The `-portable.md` variants are self-contained (no reference to humanizer's pattern library, since it isn't installed there) and sized to paste directly into:
- claude.ai Project custom instructions, or a pinned first message in a plain chat.
- ChatGPT Custom Instructions ("How would you like ChatGPT to respond?") or a Custom GPT's instructions field.

Kept short by design — full nuance lives in the non-portable versions for Claude Code; the portable versions carry only the highest-value rules (top vocabulary bans, the reasoning-chain filter, sentence-structure habits, the anti-humanization rule) so they fit comfortably under typical GUI instruction-field limits.

## Profile content

### `matt-default.md`

Adapted from `my voice profile.txt`, which was already a complete, deliberate voice guide — validated against the raw samples during this session (e.g. its "Internal Dialogue" examples like "Huh... What if I tried this?" appear verbatim in `writing samples.txt`). Carried forward essentially as-is: purpose, how Matt thinks (visual/analogy-driven), thought progression (observation → question → example → reaction → conclusion), internal dialogue, concrete-before-abstract, banned corporate vocabulary, sentence structure, no em dashes, no artificial rule-of-three, anti-humanization rule (no fake typos/slang/anecdotes), editing procedure, final three-question test.

### `matt-jira.md`

New. Built from the incident, not extrapolated:

- **Structure** (confirmed instinct): root cause first, then why it matters, then what changes, then a concrete verification step. Empathetic aside when it's genuinely relevant (owning that a mistake isn't anyone's fault) — not manufactured.
- **Reasoning-chain filter** (Codex's phrasing, used near-verbatim): preserve the instinct to explain why something happened and how to prevent it, but don't automatically include the entire reasoning chain. Ask: "Does the reader need this to make a decision or continue the work?" If not, it stays in working notes, not the ticket.
- **Plain language over precision jargon**: default simple; reach for exact technical framing only when the reader needs that level of detail to act. Worked example included: "UPN vs. SMTP suffix" (too precise, unprompted) vs. how Matt would actually phrase the same root cause.
- **Trim AI-troubleshooting narrative**: this is the director's literal complaint — the investigative play-by-play doesn't belong in the ticket body; only the actionable conclusion does.

### Portable variants

Condensed to the rules with the highest leverage per word: banned vocabulary (top 15-20 from humanizer/WRITING.md overlap), no em dashes, the reasoning-chain filter, plain-language-over-jargon, and the anti-humanization rule. Each ends with the same three-question final test as the full default profile, since that's cheap and high-value regardless of length.

## Validation

Before calling this done: run the actual (redacted) Jira incident text through `matt-jira.md` + humanizer and check the result against the director's stated complaint criteria — is it short, root-cause-first, free of investigative narrative, plain-language where jargon isn't needed? This is the one concrete before/after check available; no other ground truth exists yet.
